# Agent instructions

See `docs/fs-cli.md` for how the `fs` CLI works, and `docs/featurescript-style.md` for how to write
FeatureScript here (including selections, editing logic, and manipulator change functions).

`README.md` is for users: an overview of the repo, setup, and links. How the tools work, and anything else written for
agents, goes in `docs/`, a skill, or here.

The Python runs on Windows too: write files that are checked in or pushed with `newline=""` (or Windows writes
`\r\n`), print paths with `as_posix()`, and don't use Unix-only modules (like `fcntl`). `tests/conftest.py` makes
tests' `write_text` write `\n`.

Test FeatureScript which computes values (math, lookup tables, editing logic, manipulator change functions,
sketches) with the evaluator: FeatureScript tests in `tests/featurescript`, or Python tests using `fs_eval`; see
`docs/testing.md`. `uv run pytest` runs them all.

After changing a feature, check, test, and show it as `.claude/skills/feature-audit/SKILL.md` says: it ends with its
`fs audit` page, sent to the user.

`docs/std-functions.md` lists useful std functions, many of which std marks `@internal` (they work; use them).

For FeatureScript names, `fs doc NAME` shows a std or project symbol's signature and documentation, `fs refs NAME`
where it's used, and `fs rename NAME NEW` renames it everywhere; `fs check --fix` fixes problems with one right answer.

A "top level option" means a horizontal enum at the top of the feature (see `docs/featurescript-style.md`'s
"Horizontal enums go at the top").

Feature icons are drawn in Python and generated by `fs gen`; see `docs/icons.md` and `.claude/skills/feature-icon/SKILL.md`.

Features with a writeup (a `.md` beside the `.fs`, like `frame/robotFrame.md`) need it updated when they change; see
`docs/feature-writeups.md`.

## Backwards compatibility

Before adding anything for compatibility, see what a released document can hold: `fs changes NAME` (or
`git diff NAME/vX.Y.Z`, its release's tag) shows what's changed since its last release. Don't consider older versions of
features or documents made with them: renaming or removing parameters, changing
defaults, or changing what's built is fine, with no migration or fallback for old values. Don't add code to handle
values saved by an older version.

Never rename a released feature's constant (the name `defineFeature` is exported as, like `frcBeltCalculator`):
documents store it as the feature's type, and lose the feature if it changes. Rename its Feature Type Name and its file
instead (see `docs/featurescript-style.md`'s "Released feature constants").

The other exception is attributes, which other features and documents read back. When an attribute's format changes, either
handle old attributes or report them as an error; either is fine.
